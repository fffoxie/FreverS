## 2. Field-Number Derivation & Serializer Rules

In Frever's custom `Frever.Protobuf.ProtobufConvert` serializer:
1. Properties without custom attributes start at **Field #10** and increment sequentially, sorted alphabetically (case-sensitive) by property name.
2. Properties decorated with `[ProtoNewField(n)]` follow all non-attributed properties in increasing order of `Order`.
3. Properties decorated with `[ProtobufIgnore]` or `[JsonIgnore]` are omitted from wire serialization.

### FileInfo Example Derivation:
- `Extension` -> Field #10
- `File` -> Field #11
- `Platform` -> Field #12
- `Resolution` -> Field #13
- `Source` -> Field #14
- `Version` -> Field #15
- `UnityVersion` (`[ProtoNewField(1)]`) -> Field #16
- `AssetManagerVersion` (`[ProtoNewField(2)]`) -> Field #17
- `Tags` (`[ProtoNewField(3)]`) -> Field #18

## 4. Cross-Language Interoperability Validation Results

Validation was executed in both directions using `protobuf-net` (C# .NET 8) and `protobufjs` (Node.js):

1. **C# -> Node.js:** Binary fixtures exported by `Frever.Protobuf.ProtobufConvert` in .NET 8 were loaded and decoded in Node.js via `protobufjs`. All field values (IDs, names, versions, lists) matched expected values exactly.
2. **Node.js -> C#:** Binary fixtures generated by `protobufjs` in Node.js were loaded and deserialized by `Frever.Protobuf.ProtobufConvert` in C# .NET 8 without errors or field data loss.

Unit test suite integration is maintained in [`test/protobuf-interop.mjs`](../../../test/protobuf-interop.mjs).
